# Azure Blob Storage — Artifact Management

Revised for the final MVP model (see `docs/azure-blob-storage-handoff-reaction.md`) and validated against the live Azure environment on **2026-08-12**.

## Connection info

| Item | Value |
|---|---|
| **Blob endpoint** | `https://testsabbiastorage.blob.core.windows.net` |
| **Container** | `artifacts` (only container used; `artifacts-dev` is not needed) |
| **Container ACL** | `blob` — anonymous read of a known Blob URL, **no** anonymous listing (validated) |

CORS (GET, HEAD, PUT, OPTIONS) is configured and harmless; it is not required because uploads pass through Tomcat and reads are direct browser requests.

## Authentication

- Reads are **anonymous** by exact Blob URL — no SAS needed, no SAS on read.
- Writes use a container-scoped SAS held **only** by production Tomcat via `HUB_ARTIFACTS_SAS_TOKEN`. Never send it to the browser, commit it, or log it.

### SAS status (validated 2026-08-12)

- Scope: container (`sr=c`), permissions `cw` (create + write; no read/list/delete), HTTPS only (`spr=https`).
- Expiry: **2027-01-01T00:00:00Z** — add a rotation reminder (see open items below).
- Two earlier tokens were pasted into a chat session during validation and must be treated as exposed: do **not** reuse them. Generate a fresh token when wiring it into production (command below).
- Account key access is enabled (`allowSharedKeyAccess: true`, required for the SAS to work). Do not disable it without reworking upload auth.

### Generating the write SAS

```bash
key=$(az storage account keys list -n testsabbiastorage --query "[?permissions=='FULL'].value" -o tsv | head -1)
az storage container generate-sas -n artifacts --account-name testsabbiastorage \
  --permissions cw --https-only --expiry "2027-01-01T00:00:00Z" --account-key "$key" -o tsv
```

## Developer setup

Local development needs only the public endpoint and container; **no SAS token**:

```
HUB_ARTIFACTS_BLOB_ENDPOINT=https://testsabbiastorage.blob.core.windows.net
HUB_ARTIFACTS_CONTAINER=artifacts
```

Development mode disables all Blob writes. Production without a SAS configured disables writes and logs a configuration warning — a missing SAS must not be mistaken for dev mode.


## Design requirements (dev must follow)

- Stable object keys generated by the app: high-entropy random value, e.g. `3f841cec-0fd7-49c8-b2d7-8b0a45e28931`; never user-supplied; no topic/filename info in the key. Key stays stable across replacements.
- Set Blob HTTP headers on upload/replacement: `Content-Type`, `Content-Disposition` (when a download filename is needed), and `Cache-Control` requiring revalidation (e.g. `no-cache`), since URLs are stable across replacements.
- Uploads pass through an authenticated InteropHub endpoint: verify user + topic management permission + slot, validate filename/type/size, **stream** (do not buffer in memory), record uploader + time. Never hand the SAS to the browser.
- No server-side read proxying, no per-request read SAS generation, no browser-direct upload, no video (all deferred).
- Private Topic Space URLs rely solely on high-entropy unlisted keys; private artifacts must never contain content whose disclosure would cause material harm.

Superseded handoff examples (byte-array `upload()`, `download()` proxying, `generateSasUrl()`, browser-direct upload SAS) must not be re-introduced. See `docs/azure-blob-storage-handoff-reaction.md` for rationale.
