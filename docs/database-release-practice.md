# Database Release Practice

How InteropHub's MySQL schema evolves from a developer's local change to a
versioned, production-applied migration — and how the local dev database
stays in sync with production in the meantime.

## Files involved

| File | Role | Hand-edited? |
|---|---|---|
| `db/unapplied_updates.sql` | Schema/data changes for the **next** release, not yet applied to production. Grows during development; emptied right after each production release. | Yes |
| `db/vX.Y_description.sql` | One frozen, permanent record per past release (e.g. `v0.28_auth_user_admin_flag.sql`). Never modified after creation. | Yes (once, at creation) |
| `db/schema.sql` | Full-schema reference snapshot (`mysqldump --no-data --routines --events --triggers`) of the local database, taken right after a refresh/restore. | **No — generated** |
| `db/local_database_refresh.sql` | Rewrites production URLs/secrets to localhost equivalents after a snapshot restore. Separate concern from schema versioning — see `db/local_database_refresh.md`. | Yes |
| `T:\scripts\python\refresh_interophub_db.py` | Runs hourly on Nathan's machine. Once a day, when a new production backup is available, it wipes the local DB, restores the new prod snapshot, applies `local_database_refresh.sql`, applies `unapplied_updates.sql`, then regenerates `schema.sql`. No-ops if there's nothing new. | Script, not repo |
| `T:\scripts\python\restore_interophub_db_from_latest_local.py` | Same pipeline, run on demand against the most recent locally-cached backup (e.g. to reset local state mid-testing) instead of downloading a fresh one. | Script, not repo |

The two Python scripts live outside this repository, on Nathan's machine
(`T:\scripts\python`, Dropbox-backed) — they are not accessible to other
developers or to agents working in this repo. **If this process changes,
those scripts need to be updated too**, not just this doc.

## `db/schema.sql` is generated output, not source

This is the one piece of the practice most likely to be misread, including
by AI coding agents: `db/schema.sql` looks like a schema-definition file
sitting in source control, but it is `mysqldump` output, regenerated by the
scripts above every time the local database refreshes (in practice, about
once a day). It carries a `AUTO-GENERATED — DO NOT HAND-EDIT` banner at the
top for exactly this reason.

Consequences:
- **Never hand-edit `db/schema.sql`.** Any manual edit is silently
  overwritten on the next refresh.
- It is **not consumed by the application or the build** — Hibernate
  manages the live schema via `hibernate.hbm2ddl.auto=update`
  (`src/main/resources/hibernate.cfg.xml`). `schema.sql` exists purely as a
  human-readable reference of "what the schema currently looks like."
- If you need to change the schema, edit `db/unapplied_updates.sql`
  instead. `schema.sql` will catch up automatically on the next refresh.
- Because it regenerates daily, `schema.sql` is often ahead of the most
  recent `vX.Y_*.sql` file — it reflects local `unapplied_updates.sql`
  changes that haven't been released yet. Treat it as "current local
  state," not "current production state."

## Daily local refresh cycle (automatic)

Every day, `refresh_interophub_db.py` runs this sequence on Nathan's
machine:

1. Download the latest production backup (no-op if already downloaded today).
2. Drop and recreate the local `interophub` database.
3. Import the production snapshot.
4. Apply `db/local_database_refresh.sql` (prod URLs → localhost).
5. Apply `db/unapplied_updates.sql`, if non-empty.
6. Regenerate `db/schema.sql` via `mysqldump`.

After this runs, the local build works against a database that matches
production plus whatever is pending in `unapplied_updates.sql`.

`restore_interophub_db_from_latest_local.py` does the same steps 2–6
on demand, against the most recently downloaded backup, for resetting
local state mid-testing without waiting for a new daily download.

## Making a schema change during development

1. Add the DDL/DML to `db/unapplied_updates.sql` (append to the end;
   don't touch prior releases' `vX.Y_*.sql` files).
2. Apply it locally (either wait for the next automatic refresh, or apply
   `unapplied_updates.sql` manually against your local database to test
   immediately without a full refresh).
3. Commit `db/unapplied_updates.sql` along with the related application
   code, same as any other change.
4. Multiple developers/features can append to `unapplied_updates.sql`
   between releases — it accumulates everything pending for the next
   release.

**Editing statements already sitting in `unapplied_updates.sql`, vs. adding
new ones:** because nothing in this file has reached production yet, and
every refresh runs it fresh against a freshly-restored prod snapshot, there
is no live production state to migrate away from. If you're refining a
change that's already in `unapplied_updates.sql` for a feature that hasn't
released — renaming a value, fixing seed data, reordering rows — it's
usually cleaner to edit those statements in place than to append another
statement that overrides them. Save the append-only pattern above for
genuinely new, separately-motivated changes. Either way, re-run the restore
script and re-check the local database afterward (see below) — an in-place
edit is only safe if the file is still internally self-consistent (e.g. any
row-count validation in the same script still matches what you inserted).

## Syncing local admin/UI changes back into `unapplied_updates.sql`

Some data — Topic Board layouts, Topic Space stage/path definitions, and
similar admin-configurable structures — is normally edited by using the
running app itself (e.g. dragging stages/paths around on a board admin
screen) rather than by hand-writing SQL. Those edits land directly in the
local MySQL tables. They are **not** captured anywhere in source control by
that action alone, and the next local refresh (daily, or an on-demand
`restore_interophub_db_from_latest_local.py` run) wipes and rebuilds the
local database from the production snapshot plus `unapplied_updates.sql` —
silently discarding any local-only UI edit that was never written back into
the SQL file.

If you've been iterating on this kind of config locally and want it to
survive a refresh (and eventually ship to production), read the change back
out of the local database and encode it into `unapplied_updates.sql`:

1. Query the local database directly for the current state of the relevant
   tables, e.g.:
   ```
   mysql -uroot -pgoldenroot interophub -e "SELECT ... FROM es_topic_stage_definition ..."
   ```
2. Compare that against what `unapplied_updates.sql` currently produces for
   the same tables.
3. Edit `unapplied_updates.sql` to match (in place if the statements are
   already there for this not-yet-released feature — see the note above).
4. Re-run `restore_interophub_db_from_latest_local.py` and re-query the
   local database to confirm the edited file reproduces the state you
   captured in step 1.

Some blocks in `unapplied_updates.sql` are explicitly designed around this
cycle and say so inline — e.g. the Emerging Standards topic classification
snapshot carries a header comment noting it should be regenerated and
*replaced* wholesale (not appended to) the next time local classifications
change. Follow a block's own header comment when it gives more specific
instructions than this doc does.

## Releasing to production

When it's time to release (schema changes go live):

1. **Back up the production database** before making any changes.
2. Apply `db/unapplied_updates.sql` to production manually (direct SQL
   execution against the production database).
3. Verify the application against production.
4. Copy the contents of `db/unapplied_updates.sql` into a new file,
   `db/vX.Y_description.sql`, where `X.Y` is the next version number
   (check existing `db/v0.*.sql` files for the latest) and `description`
   is a short snake_case summary of the change (e.g.
   `v0.29_topic_spaces.sql`). This file is a permanent, frozen record —
   never edit it after creation.
5. Empty `db/unapplied_updates.sql` (truncate to zero bytes / no
   statements) so it's ready to accumulate changes for the next release.
6. Commit the new `vX.Y_*.sql` file and the emptied `unapplied_updates.sql`
   together, along with the corresponding application code, in one commit
   — matching the pattern of past releases (e.g. commit `ccb2d35`, which
   added `v0.28_auth_user_admin_flag.sql` alongside the app code that
   depended on it).

`db/schema.sql` needs no manual action at release time — it will pick up
the new baseline automatically on the next local refresh.

## Naming convention for version files

`db/vX.Y_short_description.sql`, matching the existing sequence
(`v0.1.sql` … `v0.28_auth_user_admin_flag.sql`). `X.Y` increments by the
next available minor version; there is no strict major-version bump rule
in use today.
